Subject matter expert playbook

What I believe about mobile architecture, and why

These are the opinions I've formed from building field apps, with the reasoning behind each one. Where I can, I've also said what would make me change my mind.

Part I

Technical philosophy

Eight things I believe that shape how I design apps.

01

Offline support is about correctness

A lot of teams ship "offline support" as a cache and a loading spinner. Then they find out in the field that nobody decided what the app should do when it can't reach the server. Offline-first means you've decided what happens to every change when there's no network: where it's saved, in what order it's sent, how duplicates are caught, and what happens when the server disagrees. If you can't answer those four questions, your app only copes with being offline until someone loses data.

02

Let the environment pick the framework

The most expensive mobile decisions I've been brought in to undo were made because a framework was easy to hire for or the team already knew it. Nobody had looked hard at where the app would run. Continuous sensor capture, a strict battery budget, a vendor hardware SDK or a two-day offline window each push you strongly one way. Start from those constraints and the right stack usually becomes obvious.

03

Enforce boundaries in code

If a layer boundary only exists in the README, someone will break it within two sprints. Put it in the code instead: module dependencies, lint rules, analyzer errors and CI checks. The architecture that lasts is the one a tired engineer can't break by accident on a Friday afternoon.

04

Write down the threading rules

Most "random" mobile crashes turn out to be concurrency bugs. Say explicitly which code runs on which thread, inject the scheduler so it can be swapped in tests, and check it with analyzers. "It worked on my phone" is how a race condition ends up on a factory floor.

05

Break startup time into steps

"Startup is slow" doesn't tell you what to fix. Time to first frame, time until the user can tap something, and time until real data shows up are three numbers with three usual causes: JIT warm-up, building the whole object graph up front, and blocking I/O. Fix whichever one is biggest, which may not be the one you noticed first.

06

Measure before you optimise, then use the data to gate releases

Crashlytics, custom keys, non-fatal errors and funnel analytics belong in the app from the start. They're how you learn that out-of-memory crashes pile up around hour four of a shift, or that 82% of people abandon a particular screen. Then use that data: if a release makes the crash-free rate worse, its rollout stops, whatever the calendar says.

07

Write for whoever maintains it in year three

Clever code costs more to maintain, and in an industrial codebase that lives for six years someone always pays for it. I aim for diffs that are easy to read, failures that are handled in plain sight, and architecture decisions written down with the reason. Then the next engineer can tell a deliberate constraint from an accident.

08

Field apps are judged on their worst moment

People judge consumer apps on the happy path. They judge field software on the moment a supervisor is standing in the rain with 1% battery and no coverage, trying to close out a shift. I check every architecture decision against that moment. What does the user see? What's safely saved? What happens if the app is killed in the middle of a write? Can they still finish the job? If the answer depends on the network, I change the design.

Part II

.NET MAUI vs. React Native vs. native
for enterprise field apps

I compare them on the four things that I've found decide how an enterprise app turns out. This is specifically about industrial, offline-first apps used in the field. It isn't a general framework comparison.

A comparison of these three only means something if you say what you're building, because the ranking can flip completely. Here I'm assuming a business app that will be around for years, runs on field or shop-floor devices, works offline for long stretches, connects to industrial hardware, and is maintained by a team. If your situation is different, my answers will be too.

Where my view comes from. My production experience is in Xamarin.iOS, Xamarin.Forms and .NET MAUI, plus native Kotlin and Swift. I have not shipped a production React Native app. The React Native column below comes from evaluating it for real projects, solving the same problems in other stacks, and reading about its architecture and the problems people have reported. I haven't maintained a React Native app myself, and I'd rather say so here than have you find out in an interview.

AXIS 1

Performance overhead

Performance overhead: .NET MAUI vs React Native vs native
Dimension.NET MAUIReact NativeNative
Execution model Compiled IL, with AOT on iOS and AOT plus R8 on Android. No interpreter on the hot path, so heavy domain logic runs close to native speed. A JS engine (Hermes) running precompiled bytecode. Business logic runs in a separate runtime from the UI it controls. That's fine for coordinating work and poor for long-running computation. Direct platform execution. The baseline everything else is measured against.
Cross-boundary cost P/Invoke and marshalling in the binding layer. It costs something, but you can see exactly where it happens in the code. JSI replaced the old async JSON bridge, but there's still a boundary. Crossing it very often is where the memory and threading bugs show up. None. That's the whole advantage.
Memory & GC A garbage collector tuned for mobile. You have to be careful about allocations on hot paths, and about how C# and native object lifetimes affect each other. Two memory systems (the JS heap and the native heap), and an object can be kept alive across both. That makes leaks harder to find, because a JS heap snapshot only shows half of it. One memory model, either ARC or the JVM/ART collector, and the platform's own tools can see all of it.
Cold start This used to be the weak spot. AOT, careful trimming, lazy DI and compiled bindings get it to an acceptable level. See the Hilti work. Precompiled Hermes bytecode and lazy bundle loading help a lot, but starting the runtime still sits on the critical path. As fast as it gets. There's no runtime to start.
Sustained background load Reliable for background sync and scheduled work via platform services. Anything continuous needs native modules. Long-running capture shouldn't live in the JS runtime. Clear winner Continuous GPS, sensor streams and tight battery budgets belong here.

Verdict: for a data-heavy business app, MAUI's overhead can be managed and mostly affects startup. React Native's overhead sits at the boundary and grows with how often you cross it, which is exactly the wrong shape for continuous telemetry. Native wins clearly on sustained load, and that's the only place where the win is worth writing everything twice.

AXIS 2

Code shareability

Code shareability: .NET MAUI vs React Native vs native
Dimension.NET MAUIReact NativeNative
Realistic UI sharing High for forms, lists, dashboards and data entry, which is nearly all of an MES or inspection app. Much lower for custom graphics. High, though the platforms differ more than teams expect once you take accessibility and platform conventions seriously. None. You can share the spec, but each platform gets its own code.
Domain & persistence sharing Strongest of the three One language from the ViewModel through the domain to EF Core and SQLite. Often it's the backend team's language too, so DTOs and validation rules can actually be shared. TypeScript domain logic shares well, including with the web app. Storage and background work still need native code someone owns. Only through KMP or by maintaining two implementations by hand. Both cost real effort.
Where sharing breaks Custom rendering, deep platform integration, and any platform feature newer than the framework's support for it. Anything continuous, close to the hardware or performance-critical. Each of those needs a native module you write and maintain. N/A. Nothing is shared, so nothing breaks.
What to expect Very high sharing on business screens. The rest is handlers and platform services. High sharing in the JS layer, plus native code that teams keep underestimating when they plan. Plan and budget for two implementations. The upside is that neither one fights a framework.

Verdict: code sharing can't be summed up in one percentage, and projects that plan around one usually get it wrong. Ask three questions: how much of the UI is shared, how much of the domain is shared, and how much native code is left over. For industrial business apps, MAUI shares the domain and storage layers best, and that's the sharing that saves the most over the years.

AXIS 3

Ecosystem maturity

Ecosystem maturity: .NET MAUI vs React Native vs native
Dimension.NET MAUIReact NativeNative
Library breadth Fewer UI and consumer packages. Very good for enterprise needs like data access, serialization, resilience, validation and identity. Widest by far There's a package for nearly everything. How good and how well maintained they are varies a lot. The whole platform, plus every vendor SDK, since vendors ship native SDKs first.
Industrial hardware SDKs Usually needs a binding or a thin wrapper you write and own. Usually needs a native module you write and own. First-class Scanner, printer, RFID and inspection camera vendors ship Android and iOS SDKs. Everyone else wraps those.
Tooling & diagnostics Visual Studio, dotnet-trace and the rest of .NET's profiling tools. Strong, if you know them. Flipper and Hermes debugging plus the platform tools. Bugs that cross the JS/native boundary are still hard to track down. Xcode Instruments and the Android Studio profiler. By a wide margin the best diagnostic tools on either platform.
Hiring pool Fewer mobile developers, but lots of .NET developers who get up to speed quickly on a well-organised codebase. Largest It overlaps directly with web hiring. Two separate specialist hires, or one generalist per platform.
Platform-feature lag Behind platform releases until the framework catches up. Behind too, though you can write the native module yourself. No lag Every new feature is available on day one.

Verdict: React Native wins on breadth and hiring. Native wins on hardware and debugging tools. MAUI wins on the enterprise data libraries that industrial business apps rely on. If what sets your app apart is a vendor hardware integration, that should decide it. The real ecosystem question is who ships an SDK for the thing your product depends on.

AXIS 4

Long-term maintainability

Long-term maintainability: .NET MAUI vs React Native vs native
Dimension.NET MAUIReact NativeNative
Upgrade burden A yearly .NET release with documented migration steps and LTS versions. Easy for an enterprise to plan around. Frequent releases with real breaking changes. Most of the maintenance cost comes from the dependency tree, more than from the framework itself. Annual OS cycles with long deprecation windows and first-party migration guidance.
Dependency risk Low A small set of dependencies, mostly from Microsoft or well maintained. Highest Deep dependency trees, where an abandoned package four levels down can hold up a platform upgrade for months. Lowest Mostly first-party frameworks with vendor-supported SDKs.
Type safety end to end Strong. Nullable reference types, analyzers and compiled bindings turn whole kinds of bugs into build errors. Strong if you're strict with TypeScript. But the native module boundary is only as typed as you make it, and nothing checks that. Strong on both platforms (Kotlin null safety, Swift optionals), enforced by the compiler.
Onboarding a new engineer One language, one way of thinking, one debugger. A .NET backend engineer gets productive quickly on a clean codebase. Quick for web engineers in the JS layer. Slow at the native boundary, which people tend to avoid, and that's where the hard bugs are. Slowest overall, but the mental model is the platform itself, which never becomes obsolete knowledge.
Five-year outlook Backed by Microsoft with a clear enterprise focus. The ecosystem will keep changing, and clean layering protects you from that. You should be doing that anyway. A large community and an architecture that keeps changing. Past migrations have been a lot of work. Safest possible bet. The platforms are not going anywhere.

Verdict: over five years, the number of dependencies is the best predictor of maintenance cost I've seen. It matters more than the language or the framework. MAUI and native both keep that number small. React Native's huge package ecosystem is its biggest strength in year one and its biggest maintenance cost a few years later.

How I actually decide

Four questions, in order. The first one that returns a hard answer decides it.

  • 1. Does the product depend on continuous sensor capture, a vendor hardware SDK, custom high-performance rendering, or a strict battery budget? Then I use native for that part. It can be native for that module and cross-platform for the rest. A hybrid split that's drawn on purpose is a perfectly good architecture.
  • 2. Is it a business app that will live for years, with lots of data and a big offline data model, at a company that already runs on .NET? Then .NET MAUI. Sharing the domain and storage code, having few dependencies and the LTS releases all pay off more each year, and your existing team can maintain it.
  • 3. Is getting to market and iterating quickly the main constraint, and do you already have a web codebase and web engineers? Then React Native, on one condition: someone on the team properly owns the native modules. The React Native projects I've seen struggle in this domain struggled at the native boundary. The JavaScript was fine.
  • 4. None of these fit cleanly? Then I prototype the riskiest technical requirement in two of the options, a week each. A week of evidence costs less than a year of regret, and a prototype answers questions a comparison table can't.
What would change my mind

If Kotlin Multiplatform keeps improving at its current pace, question 2 gets a serious fourth answer. Native UI on both platforms on top of a shared domain layer is, architecturally, what most teams actually want. I'm following it closely, and I'm happy to change my answer when the evidence changes.
